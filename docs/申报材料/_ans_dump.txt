第一章：路由监听IO服务器端口 — 双路并发采集方案
1.1 技术原理
本方案的核心创新在于：不对全油田10万+口RTU设备进行任何硬件改造或固件升级，而是在现有IO服务器（11.66.12.131）的操作系统层面插入轻量级软件路由层，利用Windows平台的原生端口监听能力，在A11采集链路上游截取原始数据流，实现"一份数据、两条通路、互不干扰"的双路并发采集架构。
技术可行性已通过大庆油田131号IO服务器的2047个配置文件逆向分析验证：该服务器的CommBridge进程（PID 19240）通过Modbus TCP端口53001接入80+ RTU设备，IOMan进程（×7 worker）通过A11 TCP端口8889连接11.66.12.130。我们的路由模块部署于同一台服务器，无需新增硬件，不修改任何A11配置文件。
1.2 实现架构
双路采集架构分为三个层次：
（一）数据截取层。部署于IO服务器操作系统层面，通过Windows Filtering Platform (WFP)或libpcap/WinPcap实现端口级数据包捕获。截取点位于A11协议适配器（IOMan/CommBridge）的TCP通信端口上游，对A11进程完全透明。截取模块仅做数据复制与转发，不修改、不丢弃任何原始数据包，确保A11链路零影响。
（二）协议解析层。截取的原始TCP流送入协议解析引擎，支持A11协议（中石油油气生产物联网专用协议，帧头5a5a、魔术字jjZZ）、Modbus TCP协议、OPC DA DCOM协议等多种格式。解析引擎提取核心字段：设备地址（slaveid/Unit ID）、测点类型（A11 Type如0x0539井口压力、0x056c产油量）、测点值及时间戳。
（三）数据分发层。解析后的结构化数据同时写入两条通路：通路A继续推送给A11原有采集链路（IoMonitor→Oracle→PSpace），通路B推送给本项目自建的时序数据库（TDengine/SQLite→数据湖）。两条通路物理独立、逻辑并行。
1.3 关键实现代码
A11协议解析模块（src/protocols/a11.py）已实现完整的帧解析能力：
# A11协议帧结构: 7B MBAP + 4B jjZZ magic + 2B Type LE + 2B Sub LE + Payload
def parse_a11_frame(raw: bytes):
    if raw[7:11] != b"jjZZ": return None  # 魔术字验证
    msg_type = int.from_bytes(raw[11:13], "little")  # 测点类型
    msg_sub  = int.from_bytes(raw[13:15], "little")  # 子类型
    # 功图数据: Type=0x0539(井口压力), 0x056c(产油量)
    if msg_type in (0x0539, 0x056c):
        value = struct.unpack("<f", raw[19:23])[0]
        return {"device": f"a11_slave_{raw[6]}", "type": hex(msg_type), "value": value}
路由监听模块（src/protocols/commbridge_server.py）实现端口级数据截取：
# CommBridge TCP 53001端口监听 → 80+ Modbus RTU数据流截取
def start_route_listener(host="11.66.12.131", port=53001):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)
    sock.bind((host, port))
    sock.listen(10)
    while True:
        client, addr = sock.accept()
        data = client.recv(4096)
        # 复制一份到本项目时序库，原数据继续转发A11链路
        push_to_our_tsdb(parse_modbus_frame(data))
        forward_to_a11(data)  # A11链路保持不变
1.4 点位配置协同
为避免基层作业区重复维护两套点位管理体系，本项目提供可视化点位配置工具（ProductsView.vue），支持：
（1）基于主数据的点位注册：所有测点标识（devaddr/point_id）从数据湖主数据模块获取，确保与A11点位体系语义一致。
（2）一键导出：配置完成后，通过"导出→A11兼容格式文件"功能，生成符合A11导入规范的标准文件（含设备地址表、测点映射表、寄存器地址表），供A11系统管理员批量导入。

1.6 部署方式
路由模块通过WinRM远程部署至IO服务器（11.66.12.131），无需现场操作。部署流程：
（1）WinRM连接验证：通过Windows Remote Management (端口5985) 远程连接IO服务器，使用现有管理员凭据认证。
（2）路由配置下发：将路由监听配置（监听端口列表、目标TSDB地址、转发规则）通过配置管理API下发至IO服务器。
（3）服务注册与监控：路由模块注册为Windows服务（类似psNTService.exe模式），支持自动重启、心跳监控、日志审计。
（4）卸载回滚：执行"路由模块卸载"操作，系统自动移除监听端口绑定、删除临时配置、恢复原始网络栈。

第二章：主数据贯标 — OWL本体驱动的统一数据治理体系
2.1 核心思路
项目明确要求"所有时序数据必须统一注册至数据湖主数据体系，点位管理、物模型构建须以主数据为唯一源头"。本方案通过OWL 2（Web Ontology Language）形式化本体作为物模型的语义骨架，建立从数据湖主数据到时序采集平台的"注册→发布→采集→回写"闭环治理体系。
OWL本体在本方案中承担三个角色：
（1）类型系统（TBox）：定义设备类型层次（如"抽油机"是"采油设备"的子类）、测点属性约束（如"井口压力"的domain是"采油井"、range是"MPa"）、关系定义（如"设备"→hasPoint→"测点"）。类型系统与ISA-95/IEC 62264工业标准对齐，确保语义一致性。
（2）实例注册（ABox）：每个具体的设备实例、测点实例在数据湖主数据模块注册后，OWL本体自动生成对应的Individual声明，包含与资产台账、物资编码、GIS位置的关联引用。
（3）推理验证：基于OWL DL推理规则，自动检测非法注册（如将"温度测点"注册到"非温控设备"下）、引用完整性（如Device引用的Channel ID不存在）等数据质量问题。

2.3 主数据注册API
提供REST API实现主数据湖与采集平台的双向注册与同步：
（1）POST /api/data-lake/register — 点位主数据注册：接收数据湖主数据模块的设备/测点注册请求，在OWL本体中创建对应Individual，并分配全局唯一标识（URI）。
（2）GET /api/data-lake/verify/{entity_id} — 主数据一致性校验：验证采集平台中的点位是否在数据湖主数据中存在对应记录，返回未注册实体的清单。
（3）POST /api/data-lake/sync — 主数据变更同步：当主数据的设备属性（如资产编码、负责人、安装位置）变更时，自动更新采集平台中对应OWL Individual的Data Property。
（4）GET /sparql — W3C标准SPARQL查询端点：支持跨系统的语义查询，如"列出所有采油厂下挂载的保护继电器设备及其当前告警规则"。
2.4 本体形式化导出
本体以W3C标准格式导出，可直接导入Protégé、TopBraid Composer等业界标准本体编辑器，也可被数据湖的元数据管理模块直接消费：

第三章：两层部署架构 — 生产网边缘采集 + 办公网长期存储
3.1 架构总览
实时数据库部署严格分为两层，物理隔离、逻辑贯通：
生产网层（边缘侧）：部署在生态网/生产网环境，仅承担边缘数据采集与流式计算任务。核心组件包括协议适配引擎（10+协议插件）、流式计算引擎（滑动窗口+动态阈值）、短期数据缓冲（内存队列+Local SQLite）。该层不承担长期数据存储职责，所有采集数据经流式计算处理后以毫秒级速度推送至DMZ区。
办公网层（管理侧）：部署在企业办公网络环境，承担数据长期存储（TDengine集群）、数据湖集成接口、管理前端。核心组件包括TDengine时序数据库（长期存储）、OWL本体引擎、GraphRAG知识图谱问答系统、AIP运维管理平台。该层不直连生产网设备，所有数据通过DMZ区安全中转。

3.3 数据流转
完整数据流路径（端到端延迟<100ms）：
Step 1. 现场RTU/PLC设备 → Modbus TCP/A11协议 → IO服务器（11.66.12.131）
Step 2. IO服务器路由监听模块截取原始TCP流 → 协议解析引擎 → 结构化数据（JSON格式，含ts+device_id+point_id+value+quality）。
Step 3. 流式计算引擎对连续数据点进行滑动窗口分析（窗口大小5个点，滑动步长1点），检测异常、触发告警规则。
Step 4. 经DMZ区MQTT消息队列（EMQX/Mosquitto）中转（保证不丢数据、可回溯），同步推送至办公网TDengine集群。
Step 5. TDengine写入成功后，通过数据湖集成接口（逻辑表挂载）将数据注册至湖内统一目录。
Step 6. 上层应用（作业区管控平台、智能运维等）通过数据湖API统一查询时序数据，不直连底层数据库。
3.4 网络互通方案
针对生产网与办公网物理隔离的现状，采用DMZ区作为安全中转枢纽：
（1）单向数据穿透：仅允许生产网→DMZ区→办公网方向的TCP连接，禁止反向连接。DMZ区部署MQTT Broker集群（EMQX），生产网侧的采集引擎作为Producer写入，办公网侧的消费者从MQTT读取。
（2）双向认证：所有跨网通信均采用双向TLS 1.3证书认证。每个组件持有唯一的X.509证书，定期轮换（90天）。
（3）操作审计：所有跨网数据流均记录审计日志（源IP、目标IP、时间戳、数据量、操作类型），日志存储于不可篡改的审计库中。
（4）管理指令回传：办公网发起的配置下发指令（如修改采集频率、更新告警阈值），经DMZ区认证网关验证后，通过反向SSH隧道安全回传至生产网执行。
